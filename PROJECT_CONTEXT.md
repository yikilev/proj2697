# Контекст проекта

Документ описывает продукт, целевую архитектуру и границы локального MVP. Это справочный контекст, а не поручение начать разработку или план следующих действий. Описанная возможность не считается реализованной до появления и проверки соответствующего кода.

## Продукт

Система ищет выпускные квалификационные работы по свободному описанию интересующей темы. Пользователь вводит текст в UI, бэкенд возвращает существующие работы в порядке убывания релевантности.

Поиск гибридный: BM25 находит совпадения по словам, семантический канал — близкие по смыслу описания. Эмбеддер преобразует текст в вектор; поиск выполняется сравнением этого вектора с векторами работ. Два рейтинга объединяются в один.

Самостоятельный режим `bm25` работает без эмбеддера и векторов. Он выбран по умолчанию и допускает запуск без корпуса с последующей загрузкой через HTTP. `hybrid` требует явно подключённого эмбеддера; автоматического перехода на BM25 нет.

Это retrieval-часть будущего RAG-приложения. В MVP нет LLM-генерации ответов, придуманных карточек и обучения нейросети.

## Масштаб и архитектура

Рабочее допущение — локальный компьютер, небольшой поток запросов и до примерно 10 000 коротких карточек. Корпус и поисковые структуры помещаются в память. Основной язык — русский. CPU достаточен для базового запуска; конкретная скорость зависит от устройства и модели.

Архитектура — один модульный бэкенд, UI как клиент и локальная SQLite-БД. BM25, эмбеддер, поиск по векторам, объединение рейтингов и индексация являются частями одного проекта. Отдельные микросервисы не нужны.

```text
UI → HTTP API → сервис поиска
                   ├── BM25 по текстам
                   ├── эмбеддер запроса → поиск по матрице векторов
                   └── объединение рейтингов → карточки → UI

JSON-корпус → локальная индексация → SQLite
SQLite → загрузка карточек и векторов в память при старте API
PUT /theses → подготовка BM25 → SQLite → публикация нового сервиса без перезапуска
```

UI взаимодействует с бэкендом только через API. Он не обращается напрямую к БД и эмбеддеру, не пересчитывает релевантность и не меняет порядок выдачи. Разработка самого UI не подразумевается задачей на бэкенд.

## Технологии и границы модулей

Фактический стек: Python 3.12.10, FastAPI, Uvicorn, Pydantic, SQLite через стандартный `sqlite3`, rank_bm25 и NumPy. Для тестов — pytest и httpx. Настройки читаются стандартной библиотекой; pydantic-settings и sentence-transformers не подключены. Совместимость с первоначально целевой Python 3.11 пока не проверена. Версии зависимостей фиксируются по фактически проверенному окружению.

Планируемый эмбеддер (адаптер пока не реализован и не проверен с настоящими весами) — `intfloat/multilingual-e5-large`, локально через sentence-transformers; размерность вектора — 1024. Первичная установка зависимостей и получение весов могут требовать интернета. Для автономной работы предполагается подготовленная локальная модель. Скорость inference на CPU зависит от оборудования; замена модели требует повторного вычисления векторов всего корпуса. Параметры модели описаны в её [официальной карточке](https://huggingface.co/intfloat/multilingual-e5-large).

Узнаваемые каталоги и их ответственность:

| Каталог или файл | Назначение |
| --- | --- |
| `main.py` | Сборка приложения и жизненный цикл |
| `api/` | HTTP-роутеры, схемы и получение зависимостей |
| `config/` | Настройки |
| `domain/` | Карточки и внутренние результаты поиска |
| `services/` | Поиск, индексация, подготовка текста и объединение рейтингов |
| `infrastructure/` | SQLite и локальные поисковые структуры |
| `external/` | Контракт эмбеддера и проверка векторов; реального адаптера пока нет |
| `scripts/` | Существующий вспомогательный CLI; не часть обязательного сценария |
| `tests/` | Проверки поведения |

Это границы ответственности, а не обязательное подробное дерево. В небольшом модуле допустим один файл с несколькими связанными функциями или классами. Вложенные пакеты появляются только при реальной необходимости. Пустые каталоги не нужны.

Обычный путь запроса: роутер → сервис поиска → репозиторий и эмбеддер. Формула объединения — обычная чистая функция. Отдельный слой use cases, общий фасад и базовый репозиторий для единственной реализации отсутствуют. Нижние слои не зависят от FastAPI.

## Данные

Единица поиска — одна работа. Ей соответствуют одна карточка, один BM25-документ и, в режиме hybrid, один вектор.

Программная полная индексация принимает UTF-8 JSON-массив карточек. Для HTTP-импорта этот массив передаётся в поле `cards` JSON-объекта:

```json
[
  {
    "id": "thesis-001",
    "title": "Гибридный поиск научных работ",
    "abstract": "Поиск по описаниям с использованием BM25 и эмбеддингов.",
    "keywords": ["BM25", "эмбеддинги"],
    "author": "Иван Иванов",
    "year": 2025,
    "url": "https://example.org/theses/001"
  }
]
```

`id`, `title`, `abstract` — обязательные непустые строки после strip. ID уникален, стабилен и не содержит `/`. `keywords` по умолчанию равен пустому списку. Автор и год необязательны. `url` — обязательная HTTP(S)-ссылка на страницу работы у источника: через неё пользователь переходит к оригиналу. Дубли ID и пустой корпус являются ошибкой импорта. Одинаковые названия разных работ допустимы. Полные тексты ВКР, PDF и другие вложения не скачиваются и не хранятся; локально остаются только поисковые карточки, ссылки и эмбеддинги.

`data/sample_theses.json` содержит шесть реальных записей из [каталога ВКР НИУ ВШЭ](https://www.hse.ru/edu/vkr/), проверенных 11 ноября 2026 года. Названия, авторы и годы взяты с индивидуальных страниц, указанных в `url`; ID образован из идентификатора страницы с префиксом `hse-`. Служебные дефисы вокруг отсутствующих частей ФИО убраны, недостающие имена не восстановлены. Поле `abstract` — составленный краткий пересказ опубликованной аннотации, а не дословный авторский текст. Ключевые слова подобраны по содержанию. Набор предназначен для примеров импорта и поиска; автоматический сбор сайта и генерация описаний не являются функциями бэкенда.

Поисковый текст состоит из названия, ключевых слов и описания, разделённых переводами строк. Автор, год и URL в ранжировании не участвуют. Поиск по полным PDF отсутствует.

## Хранение и индексация

SQLite хранит карточки, а для полного индекса — также векторы и модельные метаданные. BM25 может использовать корпус без векторов. Отдельные NPZ-файлы, векторная БД и второй источник карточек не нужны. Простого явного SQL достаточно; ORM и универсальный слой доступа к данным не требуются.

В режиме bm25 `PUT /theses` полностью заменяет корпус карточками непосредственно из JSON-тела. После валидации строится новый BM25-сервис в памяти, затем `SQLiteStorage.replace_cards` транзакционно сохраняет корпус, удаляя прежние векторы и метаданные. Только после успешной записи публикуется новый сервис и возвращается 200. Ошибка подготовки или записи сохраняет предыдущую БД и активный поиск. Импорты сериализуются простой блокировкой экземпляра приложения; запись и публикация находятся в одном защищённом участке.

Программный интерфейс полной индексации сохраняется: читает JSON, валидирует записи, вычисляет векторы батчами и сохраняет согласованный набор данных одной транзакцией. Ошибки подготовки не приводят к публикации части корпуса. Отдельная CLI-логика не развивается и не требуется для загрузки BM25-корпуса.

Эмбеддинги связаны с ID работ. Их формат хранения однозначен и не использует pickle: например, float32 BLOB с известной размерностью. Метаданные содержат идентификатор и версию модели, размерность, нормализацию и версию подготовки текста. При загрузке проверяются соответствие карточек векторам, корректность формы и совместимость модели. Равная размерность разных моделей не означает совместимости.

При старте API сохранённые карточки загружаются в память, BM25 строится из текстов; hybrid также загружает векторы. Каждый запрос работает с одним неизменяемым снимком этих данных. Дочитывание изменившихся карточек из БД во время поиска не требуется. После успешного HTTP-импорта последующие запросы используют новый корпус без перезапуска. Уже начатый запрос может завершиться на старом снимке. Изменения SQLite внешней программой автоматически не отслеживаются; для программной переиндексации hybrid по-прежнему нужен перезапуск. Параллельные внешние индексаторы и инкрементальные изменения не поддерживаются.

Пользовательский сценарий без эмбеддера: запуск API с одним worker → `PUT /theses` с JSON-телом → `POST /theses/search` с JSON-параметрами. `DATABASE_PATH` и `LOG_LEVEL` остаются настройками процесса.

## Поиск и ранжирование

BM25 использует одинаковую простую токенизацию документов и запросов: нижний регистр, замена `ё` на `е`, выделение буквенно-цифровых токенов. Лемматизации и словаря синонимов в MVP нет. Кандидаты имеют хотя бы один общий токен с запросом; отсутствующие совпадения не заменяются случайными документами для заполнения лимита. Знак BM25 score сам по себе не является проверкой наличия совпадения.

Эмбеддер получает естественный текст. Внутри адаптера E5 запросу добавляется `query: `, документу — `passage: `. Префикс добавляется один раз. Векторы L2-нормализованы. Семантический поиск — точное скалярное произведение нормализованных векторов через NumPy. Эмбеддинги корпуса не вычисляются повторно при запросе.

Длина входа ограничена моделью. Для E5 учитывается окно в 512 токенов вместе со служебными токенами. Обрезка допустима и описана как ограничение; индексация сообщает число обрезанных карточек. Полный abstract в ответе не означает, что весь текст поместился в модель.

Рейтинги объединяются Reciprocal Rank Fusion:

```text
score(d) = 1 / (60 + bm25_rank(d)) + 1 / (60 + semantic_rank(d))
```

Позиции начинаются с 1. Отсутствующий в канале документ получает нулевой вклад этого канала. Сырые BM25 score и cosine similarity напрямую не складываются. Веса каналов, min-max-нормализация и reranker отсутствуют.

Базовый лимит кандидатов каждого канала — 100, ограниченный размером корпуса. `top_k` по умолчанию равен 10, допустимы значения от 1 до 100. Лимит кандидатов фиксирован и не меньше допустимого top_k до ограничения размером корпуса.

Результаты объединяются по ID, сортируются по убыванию RRF score, при равенстве — по строковому ID по возрастанию. Такой же дополнительный ключ используется в каждом канале. Округление до сортировки отсутствует. В выдаче не больше top_k уникальных работ.

Score — относительная поисковая оценка, не вероятность и не процент соответствия. Порог релевантности не задан: даже для темы вне корпуса семантический канал возвращает ближайшие работы. Достаточная тематическая близость без отдельной оценки качества не гарантируется.

## API

| Метод и путь | Результат |
| --- | --- |
| `PUT /theses` | Полная замена корпуса в bm25, немедленное обновление поиска; 409 в фактическом hybrid |
| `POST /theses/search` | Отсортированные работы по описанию темы |
| `GET /theses/{thesis_id}` | Карточка без поискового score; 404 для неизвестного ID при загруженном корпусе, иначе 503 |
| `GET /health` | Готовность компонентов и размер загруженного корпуса |

Тело запроса поиска:

```json
{"query": "Поиск научных работ с помощью нейросетей", "top_k": 10, "debug": false}
```

Запрос после strip непустой, содержит букву или цифру и не превышает 4000 символов. `top_k` — целое число в допустимом диапазоне, `debug` — bool. Неизвестные поля и неверные типы отклоняются с 422.

Ответ содержит `query`, `count`, `results`. Поле `query` — текст после strip без модельного префикса. `count` — число возвращённых работ. Каждый элемент `results` содержит поля карточки и итоговый `score`. При `debug=true` добавляются `bm25_score`, `semantic_score`, `bm25_rank`, `semantic_rank`; для отсутствующего канала они равны null. При `debug=false` этих полей нет. Диагностика не меняет рейтинг.

Импорт принимает `{"cards": [...]}`. Пустой список, дубли ID после нормализации, невалидные карточки и неизвестные поля отклоняются с 422 до изменения данных. Успешный ответ — 200 с `{"status":"ok","documents_count":1,"search_mode":"bm25"}`. Ожидаемая недоступность хранилища возвращает 503 без SQL и серверных путей. Фактический режим определяется сборкой приложения: явно внедрённые гибридные зависимости имеют приоритет над `SEARCH_MODE`.

Успешный `/health` возвращает 200 с `status: "ok"`, `index_loaded: true`, положительным `documents_count`, `search_mode` и `embedding_model` (`null` для bm25). До первого импорта в bm25 возвращается 503 с `{"status":"not_ready","index_loaded":false,"documents_count":0,"search_mode":"bm25","embedding_model":null}`. Поиск и получение карточки до импорта также возвращают 503. Оба состояния health описаны в OpenAPI. Health и импорт не требуют активного поискового сервиса; health не запускает inference. CRUD отдельных карточек, multipart, загрузки URL, пагинации и отдельных публичных ручек BM25 или эмбеддера нет.

## Жизненный цикл и надёжность

Приложение работает с одним worker. Сохранённые поисковые данные и зависимости загружаются в lifespan; HTTP-импорт BM25 создаёт новый снимок. Импорт модулей не загружает веса и БД. Синхронные обработчики FastAPI выполняются в thread pool. SQLite и построение BM25 не блокируют event loop, одновременный encode одной модели ограничен простой блокировкой.

Невалидные внешние данные проверяются на входе. Данные уже проверенного неизменяемого снимка не валидируются заново в каждом слое. В bm25 отсутствие файла БД допускается: `/docs`, импорт и health доступны сразу. Повреждённая БД, неверная схема, пустой сохранённый корпус и ошибки доступа прерывают startup; они не считаются отсутствующим корпусом и не исправляются перезаписью существующей БД. В hybrid отсутствие индекса или настоящего эмбеддера остаётся ошибкой startup. Ожидаемый сбой эмбеддера во время запроса соответствует 503; программная ошибка не маскируется пустой выдачей или успехом только BM25.

Поддерживаются только настройки окружения `SEARCH_MODE`, `DATABASE_PATH` и `LOG_LEVEL`; `.env` автоматически не читается. Настроек модели, устройства и размера батча в окружении нет. Относительный `DATABASE_PATH` разрешается от корня проекта; пути при прямом программном вызове хранилища и чтении JSON — от рабочего каталога вызывающего кода. Стандартного logging достаточно; полный корпус, матрицы и запросы пользователей по умолчанию не логируются.

Проверяемые свойства — корректное объединение рейтингов, отсутствие дублей, стабильная сортировка, соблюдение top_k, согласованность сохранённых данных и HTTP-контракт. Обычные тесты работают с фиксированными fake-векторами без сети и GPU. Они не доказывают качество реальной модели. Интеграционная проверка настоящих весов и оценка релевантности на размеченных примерах — отдельные виды проверки.

## Границы версии

В MVP отсутствуют микросервисы, внешние поисковые серверы, отдельная векторная БД, очереди, Redis, Kubernetes, агентные фреймворки, LLM, OCR, обработка PDF/DOCX, чанкинг, авторизация, админка и фоновая синхронизация. Docker не является условием запуска.

Новые возможности появляются только по отдельной задаче. Архитектурные заготовки под них не требуются. README отражает фактическую реализацию, команды запуска и известные ограничения; этот документ описывает целевой продукт.
