# Поиск выпускных квалификационных работ

FastAPI-бэкенд для гибридного поиска ВКР. Завершён этап «вся прикладная логика
написана, реальные интеграции не подключены». Реализованы локальные алгоритмы,
сервисы индексации и поиска, а также HTTP-маршруты `/theses/search`,
`/theses/{thesis_id}` и `/health`. Реальных адаптеров SQLite и модели
эмбеддингов пока нет: обычный запуск прерывается на startup с понятной ошибкой
отсутствующих интеграций. Fake-компоненты используются только в тестах.

Реализованы карточка ВКР (`domain.models.Thesis`) и схемы поиска
(`api.schemas`). `SearchResponse.from_results(request, results)` оформляет
готовые результаты: при `debug=true` сохраняет все четыре диагностических
поля, включая `null`, при `debug=false` исключает их из ответа. Поля карточки
и `score` находятся непосредственно в каждом элементе `results`.

## Локальные алгоритмы

- `services.indexing.build_search_text(thesis)` собирает название, строку
  ключевых слов через пробел и описание с разделением переводами строк.
  При пустом списке ключевых слов средняя строка пустая. Автор, год, URL и ID
  в поисковый текст не входят.
- `infrastructure.search.BM25Index(ids, texts).search(query, limit=100)`
  использует `rank_bm25.BM25Okapi`. Общая функция `tokenize` приводит текст
  к нижнему регистру, заменяет `ё` на `е` и выделяет буквенно-цифровые
  Unicode-токены. Кандидат должен иметь общий токен с запросом, даже если
  его оценка нулевая или отрицательная. Без совпадений возвращается пустой список.
- `infrastructure.search.SemanticIndex(ids, vectors).search(query_vector, limit=100)`
  вычисляет точное скалярное произведение через NumPy. Строки матрицы соответствуют
  ID; матрица и готовый вектор запроса должны быть конечными и L2-нормализованными.
  Форма, размерность, нормализация и уникальность ID проверяются на входе.
  Нулевые и отрицательные сходства остаются кандидатами.
- `services.search.reciprocal_rank_fusion(bm25_hits, semantic_hits, top_k=10)`
  принимает уже отсортированные списки `domain.models.SearchHit` с уникальными
  ID внутри каждого канала. Складывает `1 / (60 + rank)`, начиная позиции с 1,
  и возвращает уникальные `FusedHit` с исходными оценками и позициями каналов.
  Отсутствующий канал даёт нулевой вклад; его диагностические поля равны `None`.

Оба канала и RRF сортируют по убыванию полной оценки, затем по строковому ID
по возрастанию; лимит применяется после сортировки. Нулевой лимит возвращает
пустой список, отрицательный отклоняется. HTTP-валидация `top_k` остаётся 1–100.
Алгоритмы работают в памяти и не обращаются к БД, энкодеру или сети.

## Сервис поиска

`services.search.SearchService(storage=..., encoder=...)` при создании один раз
загружает и проверяет согласованный снимок через `load_index`, строит BM25 и
семантический индекс. Карточки связываются с векторами по ID, независимо от
порядка в снимке. API использует этот снимок до завершения lifespan.
После переиндексации новый корпус доступен только после перезапуска API.

```python
from api.schemas import SearchRequest
from services.search import SearchService

service = SearchService(storage=storage, encoder=encoder)
response = service.search(SearchRequest(query="Поиск научных работ", top_k=10, debug=True))
card = service.get_thesis("thesis-001")
readiness = service.health()
```

`search` принимает валидированный `SearchRequest` и возвращает `SearchResponse`.
Кодируется только естественный текст запроса, без добавления префиксов E5.
Один экземпляр сервиса владеет энкодером для поисковых потоков приложения;
простая блокировка ограничивает одновременный `encode_query` и защищает копирование
его результата. Каждый канал получает лимит `min(100, размер корпуса)`, затем
RRF объединяет кандидатов и ограничивает выдачу `top_k`. `debug` меняет только
диагностические поля. Поиск не читает хранилище и не кодирует документы.

`get_thesis(id)` возвращает независимую копию исходной карточки без score либо
`None` для неизвестного ID. `health()` сообщает `status`, `index_loaded`,
`documents_count` и `embedding_model` без кодирования и чтения хранилища.
Ожидаемые сбои адаптер сообщает через `external.embedder.EncoderError`;
сервис пропускает их вызывающему коду. Неверные векторы и программные ошибки
также остаются ошибками, без пустой выдачи или перехода на один BM25.

## HTTP API и сборка приложения

`main.create_app(dependency_factory=...)` принимает синхронную функцию без
аргументов, возвращающую `main.AppDependencies(encoder=..., storage=...)`.
Фабрика должна создавать адаптеры внутри своего вызова. В lifespan она вызывается
один раз, затем создаётся `SearchService`: он загружает и проверяет снимок и
подготавливает индексы. Сервис становится доступен маршрутам только после
успешной подготовки. При завершении lifespan ссылка на сервис убирается из
состояния приложения. Отсутствующий или некорректный снимок и ошибки сборки
прерывают startup.

Импорт `main.py` и вызов `create_app` только описывают приложение: не открывают
БД, не загружают веса и не запускают inference. Сборка и подготовка выполняются
в пуле потоков, как и синхронные HTTP-обработчики. Нижние слои не импортируют FastAPI.

| Метод и путь | Поведение |
| --- | --- |
| `POST /theses/search` | Принимает `query`, `top_k` (1–100, по умолчанию 10), `debug` (по умолчанию false); возвращает `query`, `count`, `results` |
| `GET /theses/{thesis_id}` | Возвращает карточку без score; неизвестный ID — 404 |
| `GET /health` | Возвращает `status="ok"`, `index_loaded=true`, `documents_count`, `embedding_model` только после подготовки сервиса |

Неверное тело запроса получает 422, ожидаемый `EncoderError` при поиске — 503.
Контракт ошибок использует поле `detail`: для 422 это непустой список ошибок
валидации с `loc`, `msg`, `type`, для 404 и 503 — строка. Неизвестная карточка
возвращает `{"detail":"Работа не найдена"}`, ожидаемый сбой модели —
`{"detail":"Энкодер временно недоступен"}`, отсутствие готового сервиса —
`{"detail":"Поисковый сервис не инициализирован"}`. Ошибки не содержат выдачи.
Программные ошибки и некорректные векторы не превращаются в 503 или успешный
ответ. При `debug=false` диагностические поля полностью отсутствуют;
при `debug=true` отсутствующий канал представлен явными `null`.
Health проверяет готовность загруженного сервиса, не выполняет inference
и не является пробным запросом к модели. Без выполнения lifespan он возвращает 503.

Тесты явно передают `create_app(dependency_factory=FakeAssembly(snapshot))` и
используют `with TestClient(app) as client`, чтобы выполнить startup и shutdown.
`FakeAssembly` находится в `tests/test_api.py`; автоматической подстановки fake
в `main.app` нет.

## Индексация

`services.indexing.build_index(input_path, encoder=..., storage=..., batch_size=32)`
читает UTF-8 JSON-массив, валидирует карточки, отклоняет пустой корпус и дубли ID
после strip. Подготовленные тексты передаются энкодеру батчами. После проверки
всех результатов сервис ровно один раз вызывает `storage.replace_snapshot(...)`.
При ошибке подготовки хранилище не изменяется. Результат `IndexingResult` содержит
`cards_count` и `truncated_count` — сумму числа обрезанных текстов из ответов энкодера.

Две границы интеграции описаны через `Protocol`:

- `external.embedder.Encoder`: описание `model`, `encode_query(text)` и
  `encode_documents(texts)`. `EncodedDocuments` содержит матрицу в порядке входных
  текстов и `truncated_count` текущего батча. Префиксы E5, реальная токенизация
  и учёт обрезки принадлежат будущему адаптеру.
- `infrastructure.storage.IndexStorage`: `load_snapshot()` читает согласованную
  версию индекса (либо возвращает `None`, если индекса нет), `replace_snapshot(snapshot)`
  атомарно заменяет карточки, векторы и метаданные. Это требование к будущему
  адаптеру, а не реализованная транзакция SQLite.

В `IndexSnapshot` строка `vectors[i]` принадлежит `vector_ids[i]`; порядок карточек
может отличаться. Метаданные содержат идентификатор и версию модели, размерность,
нормализацию и версию подготовки текста. `load_index(storage=..., model=...)`
проверяет их полное совпадение, непустоту корпуса, уникальность и соответствие ID,
форму и значения векторов. Сервис поддерживает L2-нормализованные векторы.
`validate_vectors` проверяет вещественные конечные значения и единичную L2-норму
с `rtol=1e-5`, `atol=1e-6` после преобразования в сохраняемый float32 и возвращает
независимый массив только для чтения. Семантический индекс использует тот же допуск.
Та же функция проверяет форму `(dimension,)` при кодировании запросов.
Содержимое переданного снимка не должно изменяться потребителем или адаптером.

CLI разбирает `--input`:

```bash
.venv/bin/python -m scripts.build_index --input data/sample_theses.json
```

Без подключённых адаптеров команда завершается с кодом 2 и сообщением
«Адаптеры энкодера и хранилища не подключены». Для вызова из Python зависимости
явно передаются в `scripts.build_index.main(argv, encoder=..., storage=...)`.
Относительный путь CLI разрешается от корня проекта; сервис принимает путь вызывающего кода.
Ошибки данных, файлового ввода-вывода и ожидаемый `EncoderError` дают код 2
с сообщением «Индексация не выполнена», без сообщения об успехе.

## Локальный запуск

Целевая версия Python — 3.11. Текущий код проверен на Python 3.12.10;
совместимость с Python 3.11 пока не проверялась.

Из корня проекта:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

Если локальное окружение `.venv` уже создано, первый шаг можно пропустить.
`requirements-dev.txt` включает `requirements.txt` и зависимости тестов.
Для установки только прикладных зависимостей используется
`python -m pip install -r requirements.txt`. В этих списках нет библиотеки
реального энкодера; установка зависимостей не загружает модель.

Обычный запуск `python -m uvicorn main:app` **сейчас завершается ошибкой startup**:
«Адаптеры энкодера и хранилища не подключены.
Передайте сборку зависимостей в create_app(dependency_factory=...)».
HTTP-сервис и Swagger UI при таком запуске недоступны.
Для рабочего запуска необходимы реальные адаптеры и совместимый готовый индекс;
их реализация в текущую версию не входит. После подключения сборки Swagger UI
будет доступен на `/docs`, схема OpenAPI — на `/openapi.json`.
Предполагается один worker.

## Тесты

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Тесты проверяют валидацию карточек и запросов, пример корпуса, сериализацию
ответов, подготовку текста, BM25, точный семантический поиск и RRF. Для
семантического поиска используются фиксированные векторы. Проверены отсутствие
совпадений, неположительные оценки, равные и близкие оценки, лимиты, отсутствующий
канал и уникальность результатов. Тесты индексации используют fake-энкодер и
хранилище в памяти только из `tests/`: проверяют импорт, батчи, соответствие ID
векторам, обрезку по отчёту энкодера, ошибки данных и векторов, несовместимость
метаданных, сохранение предыдущего индекса при сбое подготовки и CLI.
Тесты сервиса поиска проверяют путь от снимка до ответа, top_k, RRF, debug,
получение карточки, готовность, сбои энкодера и неверные векторы, параллельные
запросы, изоляцию снимка, однократную подготовку индексов и чтение хранилища,
отсутствие повторного кодирования корпуса.
API-тесты через TestClient с lifespan проверяют HTTP-контракт, сериализацию debug,
ошибки 422/404/503, видимость программных ошибок, отсутствие inference в health,
однократную сборку и подготовку индексов, отказ startup при некорректном снимке,
ошибке загрузки модели и отсутствии интеграций. Проверяются выполнение синхронных
вызовов вне потока event loop и импорт всех прикладных модулей в чистом процессе
с запретом записи файлов, открытия БД, сетевых обращений, запуска процессов
и импорта тестовых компонентов или библиотек реальной модели.

`tests/test_end_to_end.py` проходит весь путь:
`data/sample_theses.json` → батчевое кодирование детерминированным fake →
хранилище в памяти → загрузка через lifespan → HTTP-поиск → карточка → health.
Ожидаемые порядок, score и ссылки заданы независимо от поискового алгоритма.
Проверяются `top_k`, неизменность ранжирования при debug, отсутствие повторного
кодирования документов и чтения хранилища при запросах. Повторная индексация
не меняет действующий API; новый lifespan получает обновлённый корпус.
Ошибки повторного импорта оставляют предыдущий снимок пригодным для запуска API.
Сетевой порт не открывается; сеть, БД и веса модели не требуются.
Атомарность реальной SQLite и поведение
реальной модели этими тестами не проверяются. Фиксированные fake-векторы
подтверждают вычисления и контракты, но не качество релевантности.
Score — относительная оценка RRF, не вероятность; семантический канал возвращает
ближайшие карточки даже при отсутствии подходящей темы в корпусе.
Проверенное окружение: Python 3.12.10, Pydantic 2.14.3, pytest 9.2.0,
NumPy 2.4.6, rank-bm25 0.2.2, FastAPI 0.162.4, Starlette 1.10.0, httpx 0.28.1.

## Оставшаяся работа: реальные интеграции

- Адаптер E5: локальная загрузка `intfloat/multilingual-e5-large`, добавление
  `query: ` / `passage: ` ровно один раз, L2-нормализация, окно 512 токенов
  со служебными токенами и префиксом, учёт обрезки документов в каждом батче.
- Адаптер SQLite: схема карточек, векторов и метаданных, однозначная
  сериализация float32 без pickle, чтение согласованного снимка и замена
  всего корпуса одной транзакцией с сохранением старой версии при ошибке.
- Настройки и сборка реальных адаптеров для API и CLI: пути от корня проекта,
  источник и версия модели, устройство, размер батча и уровень логов.
- Интеграционная проверка с настоящими локальными весами и БД: индексация,
  загрузка, поиск, обрезка, совместимость метаданных и откат неудачной записи.

Качество релевантности требует отдельной оценки на размеченных запросах.
Она не заменяется ни fake-тестами, ни успешным запуском настоящих адаптеров.

```text
api/
    routes.py              # HTTP-маршруты
    schemas.py             # Схемы запросов и ответов
config/
    settings.py            # Настройки локального запуска
domain/
    models.py              # Карточки ВКР и результаты поиска
services/
    search.py              # Сервис поиска по снимку и чистая функция RRF
    indexing.py            # Подготовка корпуса, индексация и проверка загрузки
infrastructure/
    storage.py             # Контракт хранилища и снимка индекса
    search.py              # Токенизация, локальные BM25 и семантический индекс
external/
    embedder.py            # Контракт энкодера и проверка векторов
scripts/
    build_index.py         # CLI с явно передаваемыми зависимостями
tests/                     # Тесты контрактов и локальных алгоритмов
data/
    sample_theses.json     # Исходные примеры карточек ВКР
requirements.txt           # Проверенные зависимости каркаса и алгоритмов
requirements-dev.txt       # Зависимости тестов
PROJECT_CONTEXT.md         # Целевое поведение и границы MVP
AGENTS.md                  # Правила разработки
```

Адаптеры SQLite и энкодера отсутствуют, настройки остаются заготовкой.
HTTP-маршруты подключены и проверены на fake-сборке; обычный startup намеренно
завершается ошибкой до подключения реальных интеграций.
