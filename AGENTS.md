# Правила работы в проекте

## Назначение документов

`PROJECT_CONTEXT.md` содержит предметную область, целевое поведение и границы MVP. Этот файл содержит постоянные правила разработки. Оба документа задают контекст; их наличие не является поручением реализовать весь проект. Конкретный объём работы определяется текущей задачей пользователя.

## Главный приоритет

Предпочтителен небольшой, прямой и понятный код, выполняющий текущую задачу. Простота означает минимум необходимых компонентов при корректном поведении. Она не означает сжатые однострочники, неясные имена или один огромный файл.

Запрещено добавлять возможности и инфраструктуру только потому, что они могут понадобиться в будущем. Нет цели превратить MVP в универсальную платформу.

## Объём изменений

- Изменения относятся к текущему запрошенному поведению и необходимым для него исправлениям.
- Смежные улучшения, новые ручки, настройки и зависимости не добавляются автоматически.
- Существующая структура переиспользуется, если она не мешает задаче. Массовые переименования, переносы и косметический рефакторинг вне задачи не нужны.
- Если текущую задачу можно решить в существующих файлах, новый пакет не требуется.
- После выполнения согласованных условий и подходящих проверок работа завершается. Цикл дополнительных улучшений «на всякий случай» не нужен.
- Обычные локальные технические решения допустимы без повторного согласования. Существенная неоднозначность поведения или выход за объём задачи требует уточнения, а не самостоятельного расширения продукта.

## Файлы и слои

- Файл объединяет связную ответственность. Один класс или одна функция не обязаны иметь отдельный файл.
- Несколько связанных моделей или небольших функций допустимы в одном модуле.
- Дополнительный слой оправдан собственной логикой или реальной границей интеграции. Прослойки, только перенаправляющие вызов, запрещены.
- Не нужны вложенные пакеты ради коротких файлов, пустые каталоги и цепочки реэкспорта через `__init__.py`.
- Папки и границы из контекста — ориентир. Подробное дерево файлов не является целью и не требует искусственного заполнения.
- Число строк и файлов само по себе не является метрикой качества. Путь от запроса до результата должен легко прослеживаться.

## Функции, классы и абстракции

- Обычная функция предпочтительна для вычисления без состояния. Класс уместен для состояния, ресурса или нескольких связанных операций.
- Прямые вызовы и внедрение зависимостей через конструктор допустимы. Отдельный DI-контейнер не нужен.
- Запрещены базовые классы, фабрики, реестры, стратегии, generic-репозитории и системы плагинов без конкретного текущего применения.
- Небольшой интерфейс эмбеддера допустим для подстановки fake в тестах. Интерфейс для каждого класса не требуется.
- Простая последовательность из нескольких строк не дробится на одноразовые функции, если это ухудшает чтение.
- Небольшое сходство кода допустимо. Общая абстракция возникает при общей устойчивой ответственности, а не только похожем синтаксисе.
- Не нужны несколько одинаковых DTO и конвертеры между ними, если данные имеют один смысл.

## Проверки и обработка ошибок

- Валидация выполняется на границах: HTTP-запрос, импорт корпуса, загрузка сохранённых данных, результат эмбеддера.
- Уже валидированные внутренние объекты не проверяются повторно на каждом уровне без отдельной причины.
- Обязательные поля не становятся Optional для удобства. Нет цепочек `getattr`, `hasattr`, `isinstance` и значений по умолчанию вместо ясного контракта.
- Исключение перехватывается там, где возможно восстановление, понятное преобразование в ошибку API или освобождение ресурса. Одинаковое исключение не оборачивается и не логируется на каждом уровне.
- Запрещено маскировать сбой пустым списком, нулевым вектором или ответом об успехе.
- Retry, автоматический fallback, circuit breaker, поддержка старых форматов и запасные пути не добавляются без реального требования.
- Проверки уникальности ID, совместимости модели, размерности векторов и транзакционная запись защищают конкретные инварианты и сохраняются.
- Ошибки программы остаются видимыми. Типизация и ясные контракты предпочтительнее многочисленных страховочных веток.

## Зависимости и настройки

- Стандартная библиотека и уже установленные зависимости предпочтительны, если решение остаётся понятным.
- Новая зависимость допустима при существенном упрощении текущей функции. Собственная сложная реализация готового алгоритма ради отказа от библиотеки тоже не является простотой.
- Настраиваемыми становятся параметры, которые реально различаются между запусками. Остальные значения могут быть именованными константами.
- Поддержка нескольких БД, эмбеддеров и файловых форматов не появляется без задачи на такую поддержку.
- Локальному MVP не нужны фоновые службы и сетевые компоненты ради потенциальной масштабируемости.

## Проверки результата

- Тесты проверяют наблюдаемое поведение: выдачу, сортировку, согласованность данных и значимые ошибки.
- Не нужны тесты наличия каждого файла, тривиальных перенаправлений и отдельных строк реализации.
- Реальные веса и сеть не являются условием обычных unit-тестов. Для вычислительной логики допустим простой fake с фиксированными данными.
- Тестовая инфраструктура не должна быть сложнее проверяемого кода. Предпочтительны небольшие явные фикстуры.
- Проверки соответствуют изменению. Повторный полный прогон без новых изменений или нерешённых проблем не требуется.
- Фактически выполненные проверки отделяются от предположений. Прохождение fake-тестов не выдаётся за проверку реальной модели или качества релевантности.

## Документация и общение

- Предметные имена и обычный понятный код предпочтительнее комментариев, пересказывающих каждую строку.
- Комментарий объясняет неочевидную причину, ограничение или компромисс.
- README описывает фактический запуск и поведение; контекст не выдаётся за отчёт о готовности.
- Дополнительные планы, отчёты, архитектурные документы и шаблоны не создаются без необходимости текущей задачи.
- Итог по задаче короткий: что изменилось, что проверено, какие существенные ограничения остались. Длинный перечень предполагаемых будущих улучшений не требуется.
